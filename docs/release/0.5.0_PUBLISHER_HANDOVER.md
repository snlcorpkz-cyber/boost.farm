## 1. Что нового в 0.5.0 (changelog для Play Console)

Краткий список для поля **"What's new in this release"** (английский, до 500 символов):

```
• AppsFlyer attribution: media_source/campaign captured per user
• OneLink deep links open the right in-app screen on cold and hot start
• Server-side event redundancy via AppsFlyer S2S (opt-in)
• Premium haptics on water/bucket/celebration moments
• Stability fixes for rewarded ads on bucket placement
```

Технически релиз 0.5.0 поверх 0.4.2 содержит:

1. **Захват `media_source` в `users.acquisition_source`.** `AppsFlyerConversionListener` теперь не только логирует — он кэширует payload в `SharedPreferences`, отдаёт его веб-слою через JS-bridge (`getAfAttribution()`), и веб отправляет это в `/auth/verify-code`. В админке (`/admin → Acquisition → Creative`) теперь видно "юзер X пришёл с креатива Y".
2. **Deep link handling (OneLink).** Подписка на `subscribeForDeepLink` в `BoostFarmApplication`, кэш в `SharedPreferences`, проброс в WebView как `CustomEvent('af-deep-link', …)`. На стороне веба `App.tsx` слушает событие и роутит на `/`, `/quests`, `/friends`, `/profile` по `deepLinkValue`. Работает и для cold start, и для retargeting hot path.
3. **Server-side Conversion API через AppsFlyer S2S.** Воркер `runAppsFlyerS2SDispatch` (см. `packages/api/src/workers/appsflyerS2SWorker.ts`) каждые 30 секунд проверяет `events`, и если событие включено в allow-list (`APPSFLYER_S2S_EVENT_NAMES`), мирорит его прямо в AppsFlyer. Гарантия: даже если SDK на телефоне не доехал (battery saver, force-quit), событие зафиксируется. По дефолту **выключен** (`APPSFLYER_S2S_ENABLED=false`) — клиентский SDK уже покрывает 99% событий.
4. **Bridge API moved 10 → 11.** Новые JS-методы: `getAfAttribution()`, `getAfDeepLink()`, `consumeAfDeepLink()`. Старые веб-бандлы делают feature-detect (`if (!b.getAfAttribution) return;`) и продолжают работать без изменений.

## 2. Что нужно от паблишера ДО загрузки

### 2.1 Подпись AAB вашим upload key

В этом репо `apps/android/keystore.properties` и `apps/android/keystore/` **в .gitignore** — поэтому AAB, который собрал я, **не подписан**. Паблишеру нужно собрать AAB у себя, на машине где лежит реальный upload keystore (либо подписать существующий через `jarsigner`, но проще пересобрать).

Файл `apps/android/keystore.properties` (на машине паблишера) должен выглядеть так:

```properties
storeFile=keystore/boostfarm-release.jks
storePassword=<пароль keystore>
keyAlias=<алиас, например boostfarm>
keyPassword=<пароль ключа>
levelPlayAppKey=26141ea65
appsFlyerDevKey=bJovpQFtkXdkS7pRivekVM
```

`levelPlayAppKey` и `appsFlyerDevKey` я отправляю отдельно (1Password / зашифрованное сообщение) — **в git они не лежат**.

Сам файл `boostfarm-release.jks` нужно положить в `apps/android/keystore/boostfarm-release.jks`.

### 2.2 Сборка signed AAB

```powershell
cd apps/android
./gradlew.bat clean :app:bundleRelease
```

Готовый AAB будет в:

```
apps/android/app/build/outputs/bundle/release/app-release.aab
```

Build config сам определяет, есть ли keystore: если файл существует — подписывает релизной подписью, если нет — собирает unsigned (для локальной проверки R8/proguard). Так что та же команда работает и у разработчика, и у паблишера.

Проверить, что AAB подписан:

```powershell
"$env:JAVA_HOME\bin\jarsigner.exe" -verify -verbose `
  app/build/outputs/bundle/release/app-release.aab
```

Должно быть `jar verified.`

### 2.3 (опционально) Сборка APK для финального smoke-теста

Перед загрузкой полезно поставить тот же AAB на физический девайс через bundletool:

```powershell
java -jar bundletool.jar build-apks `
  --bundle=app-release.aab `
  --output=app-release.apks `
  --mode=universal

# распаковать
Rename-Item app-release.apks app-release.zip
Expand-Archive app-release.zip app-release-unzipped

# поставить
adb install app-release-unzipped/universal.apk
```

bundletool: <https://github.com/google/bundletool/releases>.

## 4. Что задеплоить НА СЕРВЕР перед или одновременно с релизом

Серверная часть уже в `main`. На production-ноде:

```bash
cd /opt/boostfarm
git pull
docker compose up -d --build
```

После этого применить миграцию `024_appsflyer_s2s.sql`:

```bash
docker compose exec api npm run migrate
# или вручную:
docker compose exec db psql -U postgres boostfarm -f /migrations/024_appsflyer_s2s.sql
```

(точную команду подставит DevOps — она зависит от того, как у вас настроен `migrate` runner).

### 4.1 ENV переменные (опционально, для S2S)

S2S воркер по дефолту выключен. Если хотите включить — добавить в `.env` на сервере:

```bash
APPSFLYER_S2S_ENABLED=true
APPSFLYER_S2S_DEV_KEY=bJovpQFtkXdkS7pRivekVM
APPSFLYER_APP_ID=idio.boostfarm.app
APPSFLYER_S2S_EVENT_NAMES=auth.register,onboarding.tutorial_finished,EngagedD0,econ.purchase
```

⚠️ Если **уже включены** клиентские события и вы дополнительно включаете S2S — AppsFlyer **дедуплицирует** по `appsflyer_id` + `eventName` + `eventTimeInSeconds`, поэтому двойного счёта не будет. Но первые 24 часа лучше включить S2S только на одно событие (например `auth.register`) и сравнить волюм в дашборде с клиентским — должно совпадать ±5%.

## 5. Тестирование после релиза

### 5.1 Smoke-тест на новом девайсе

1. Удалить старую сборку: `adb uninstall io.boostfarm.app`
2. Поставить из Play (Internal Testing track или production after rollout).
3. Открыть приложение, пройти онбординг.
4. Через 30-60 секунд проверить **AppsFlyer → Live Events Viewer**: должны прийти `af_complete_registration`, `af_tutorial_completion`, и (если кликнули в ведро) `af_bucket_collected`.

### 5.2 Проверка captured `media_source`

После того как из тестовой кампании в Meta/Google прилетит первый юзер:

```sql
SELECT
  id,
  acquisition_source->>'afStatus'      AS af_status,
  acquisition_source->>'afMediaSource' AS media_source,
  acquisition_source->>'afCampaign'    AS campaign,
  acquisition_source->>'afAdName'      AS ad,
  created_at
FROM users
WHERE acquisition_source->>'afMediaSource' IS NOT NULL
ORDER BY created_at DESC
LIMIT 20;
```

Также видно в админке: `/admin → Acquisition → Creative tab`.

### 5.3 Проверка deep link

OneLink template создаётся в AppsFlyer dashboard → Engagement & Deeplinking → Create OneLink. После этого:

```bash
adb shell am start -a android.intent.action.VIEW \
  -d "https://YOUR_TEMPLATE.onelink.me/PARAMS?deep_link_value=quests" \
  io.boostfarm.app
```

Должно открыться приложение и роутнуться на `/quests`. В Logcat искать `BoostFarm: af-deep-link forwarded`.

## 6. Если что-то пойдёт не так

### 6.1 Play Console говорит "upload key mismatch"

Значит AAB подписан другим keystore чем тот, что зарегистрирован для приложения. Варианты:
- Использовать **тот же** upload key, что и для предыдущего релиза 0.4.2.
- Если key потерян — Play Console → App integrity → Request upload key reset (поддержка отвечает 1-3 дня).

### 6.2 R8 ругается при сборке

Все нужные keep-rules уже в `apps/android/app/proguard-rules.pro`. Единственный benign warning — `R8: The companion object Companion could not be found in class com.appsflyer.internal.AFj1kSDK`. Это известный артефакт обфускации AppsFlyer SDK 6.18.x, на работу не влияет.

### 6.3 AppsFlyer не показывает события после релиза

1. Проверить что в `keystore.properties` правильный `appsFlyerDevKey=bJovpQFtkXdkS7pRivekVM` (не пустой).
2. Logcat фильтр `tag:AppsFlyer_*` — на старте должна быть строка типа `AppsFlyer SDK init`.
3. AppsFlyer dashboard → Settings → Tracking link — убедиться что `applicationId` `io.boostfarm.app` совпадает с тем, что в AppsFlyer карточке приложения.
4. Если новый юзер не появился в Overview — подождать до 30 минут (in-app events real-time, install attribution иногда задерживается).

### 6.4 Откат

Если 0.5.0 ломает что-то критичное:
- Play Console → Production → Halt rollout (кнопка слева вверху).
- Установленные у юзеров 0.5.0 не откатятся, но новые загрузки получат 0.4.2 и снижение волюма проблемы.
- Серверная сторона полностью обратно совместима — `users.acquisition_source` JSONB просто не получит новые поля.

## 7. Запуск первой Meta-кампании

Когда AAB одобрен Play и доступен в Production:

1. **Meta Business Manager → Events Manager** → выбрать датасет, привязанный к BoostFarm.
2. **Connect app data via partner integration → AppsFlyer**. AppsFlyer уже передаёт нам события в Meta (постбэк настроен на стороне AppsFlyer dashboard, как видно из присланных скриншотов).
3. **Ads Manager → Create Campaign:**
   - **Objective:** App Promotion → App Installs (для первой кампании).
   - **Performance goal:** Maximise number of app installs.
   - **App:** выбрать BoostFarm (`io.boostfarm.app`).
   - **Optimisation event:** App Install (потом, через 50+ конверсий, переключить на `Tutorial Completion` или `EngagedD0` для качественных юзеров).
4. **Дневной бюджет:** для нового пикселя/события начинать с **$30-50/день**, чтобы Meta-алгоритм собрал learning phase (~50 конверсий).
5. **Креативы:** см. `docs/marketing/CREATIVE_BRIEF.md` — там список первых 5 креативов с UTM-конвенцией. Имена UTM напрямую попадают в `acquisition_source.afCampaign` / `afAdName` и видны в админке.

После того как пройдёт learning phase (~7 дней или 50 конверсий, что наступит раньше) — переключайте на **App Event Optimisation** на `EngagedD0` или `tutorial_completion`. Это даст качественных юзеров, не просто "скачал и закрыл".
